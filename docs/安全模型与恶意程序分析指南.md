# TwinBox 安全模型与恶意程序分析指南

> TwinBox 2.1.58 起提供「恶意程序防护」分身级开关。本文说明它能挡什么、
> 挡不住什么，以及在容器里调试恶意程序的正确姿势。读透本文再动手。

## 一句话模型

**VirtualApp 类容器对"守规矩的应用"是仿真环境，对"故意越狱的代码"只有
内核边界是真的。** 恶意程序防护做的事：把能在内核层变硬的全部变硬，
变不硬的明确告诉你。

## 两类防线（本质区别）

| 防线 | 机制 | 恶意程序能否绕过 |
|---|---|---|
| **内核级** | uid 隔离、SELinux、scoped storage、seccomp | ❌ raw syscall 也拦得住 |
| 用户态 | libc hook（IO 重定向）、binder 代理（包名/路径改写）、伪造信息 | ✅ 静态链接自己的 libc 或直接 raw syscall 即绕过 |

用户态防线的价值是**兼容性与隐私卫生**（普通 app 看到一致的世界），
**不是安全边界**——恶意程序防护不依赖它们。

## 你已经有的内核级墙（无需配置）

1. **uid**：分身与宿主同 uid，但与设备上其它 app 不同 uid——恶意程序碰不到
   其它应用的私有数据、听不到其它进程的 binder。
2. **SELinux**：分身跑在 untrusted_app 域——system 文件、其它域的资源，
   策略一律拒绝。
3. **scoped storage（Android 11+）**：宿主 targetSdk 30+ 且未申请
   MANAGE_EXTERNAL_STORAGE → 即便 raw syscall 也写不了真实 sdcard 的
   任意路径，只能写自己的专属目录。
4. **无 root**：容器进程没有 root，mount namespace 与真实系统一致。

## 2.1.58 新增：seccomp 加固（分身级开关）

开启位置：分身长按 → 恶意程序防护。

**加固模式（malwareGuard）**——分身进程在任何应用代码运行前装入
seccomp BPF 过滤器（内核级，fork/exec 出的子进程同样继承）：

- 拒绝：mount / umount2 / init_module / finit_module / delete_module /
  bpf / perf_event_open / kexec_* / reboot / swapon / swapoff /
  open_by_handle_at / name_to_handle_at / ptrace /
  process_vm_readv / process_vm_writev / keyctl / add_key / request_key /
  fanotify_init / userfaultfd / pidfd_getfd / fsopen / fsconfig / fsmount /
  move_mount / open_tree / mount_setattr / io_uring_setup
  → 一律返回 EPERM。覆盖：内核模块加载、eBPF 提权、perf 侧信道、
  跨进程内存读写（读宿主进程）、新 mount API、io_uring 攻击面。
- 不拒：unshare / splice / memfd_create 等正常程序广泛使用的调用
  （兼容优先；用户命名空间受 SELinux 约束）。

**断网加固（netIsolation）**——叠加 socket(AF_INET / AF_INET6 /
AF_PACKET) → EPERM。binder 是独立 fd 通道不受影响；DNS/TCP/UDP/原始
套接字全灭。内核级：改用 raw syscall、换静态 libc 都没用。

**生效时机**：分身下次进程启动（bindApplication 早期装载）。切换开关后
建议先结束分身再启动。

**日志锚点**：`V|MWG`（装载成功/失败）、native 侧 `MWG:`（过滤器安装
结果与指令数）。

## 挡不住的（诚实清单）

1. **内核 0day**。seccomp 缩小攻击面，不消灭。内核洞一破，什么容器都
   是纸——这是业界共识，不是 TwinBox 的短板。
2. **同 uid 数据破坏**。分身与宿主同 uid：恶意程序可以删改容器内文件、
   TwinBox 自己的设置。属可恢复损耗——分身数据本身就是要观测的靶场，
   宿主设置损坏重装即恢复，但重要分身数据请自行留备份。
3. **kill 同 uid 进程**（kill/tgkill 未拒，框架正常依赖）：恶意程序可
   杀 TwinBox 宿主进程 = DoS，非穿透。
4. **物理侧信道**：耗电、发热、声音、亮屏等一切你能物理观测的它也能。
5. **社会工程**：弹伪造界面骗你点授权——警惕性要靠自己。

## 恶意程序分析操作建议（推荐顺序）

1. **一次性设备 > 日常机**。最硬的隔离是物理隔离：二手旧手机刷完机
   专门做靶机，测完恢复出厂。日常机上测 = 接受上述残余风险。
2. **开加固 + 断网**，需要观察其网络行为时才开网，且网络侧落水槽
   （伪造 DNS/HTTP 应答的 sinkhole，如 Inetsim）而非真实互联网。
3. **有 root 的话**：AFWall / iptables 按 uid 断 TwinBox 的网——
   netd 层强制，比 app 层任何东西都硬。
4. 容器内**不登任何账号**、不插 SIM（或插废卡）、不开蓝牙。
5. 观测文件系统动向：容器文件管理器（2.1.58）+ `V|FM` 日志锚点。
6. 测完：结束分身 → 卸载分身 → 检查 `user/<id>/` 与 sdcard 视图无残留
   → 有洁癖就重装 TwinBox（宿主私有目录整体清零）。

## FAQ

- **Q：为什么不做每个分身独立的 uid？**
  A：Android 的 uid 是系统分配的，app 无权自选。独立 uid 需要系统签名
  或 root 常驻，那就不叫免 root 方案了。
- **Q：seccomp 会不会误伤正常分身？**
  A：拒绝清单避开了正常程序广泛使用的调用。已知风险点是 io_uring
  （新式异步 IO，少数新库用）——若某 app 在加固模式下异常，先关该
  分身的加固再验证是不是它。
- **Q：恶意程序能发现自己在容器里吗？**
  A：能（检测 hooks/文件系统特征是攻防常态）。防检测不是本防护的
  目标，防穿透才是。
